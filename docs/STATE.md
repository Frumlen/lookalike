Дата: сентябрь 2026.

## 1. Зачем это

Супермаркет «Меркурий», один магазин, оборот около 21 млн руб/мес,
ассортимент 14 862 позиции, учёт в 1С:Розница 2.3.

**Весовой товар — 32,7% оборота** (88,4 млн руб за 13 месяцев), 1 200 позиций.
Сейчас на весах продавец **вручную набирает номер товара**: медленно, ошибки
в номере дают неверную цену и пересортицу.

Задача: камера смотрит на площадку весов, продавец кладёт товар — на экране
появляются несколько похожих позиций, он выбирает нужную касанием.

**Первая очередь сужена до свежих овощей и фруктов на развес** — 38 классов,
133 позиции, 38,8 млн руб (14,3% оборота). Мясо, сыры, колбасы, орехи
отложены: их больше и они однороднее внешне. Позже добавились конфеты вразвес.

## 2. Как решено (и почему именно так)

**Обучения нет.** Готовая модель DINOv2 переводит кадр в вектор из 384 чисел,
где похожие предметы оказываются рядом. Распознавание — поиск ближайших
векторов среди эталонов.

```
кадр → DINOv2 → вектор → ближайшие в базе → список похожего
```

Почему не дообучение свёрточной сети: ассортимент магазина меняется постоянно,
и переобучение под каждый новый сорт груш — это тупик. При поиске по векторам
**добавить товар = положить 5–8 фотографий**, работает сразу.

Это же решение независимо выбрал Mertech в своих весах VISION-AI: их «новый
товар после 3–7 взвешиваний» и параметр «количество обучения уникальных ID:
4000» указывают именно на поиск по векторам, а не на классификатор.

### Что измерено

Проверка «убрать кадр и найти его по остальным», 1586 снимков:

| Модель | Размер | TOP-1 | TOP-3 | TOP-5 | Скорость (x86 Mac) |
|---|---|---|---|---|---|
| DINOv2-base fp32 | 331 МБ | 54,9% | 74,4% | 80,8% | 886 мс |
| DINOv2-base int8 | 88 МБ | 41,6% | 60,5% | 68,1% | 824 мс |
| **DINOv2-small fp32** | **84 МБ** | **54,3%** | **74,3%** | **79,8%** | **260 мс** |

Проценты приведены по папкам (144 класса). Если схлопнуть дубли артикулов
в классы товара (55 классов), **TOP-1 поднимается до 87,3%**: большая часть
«ошибок» — это один и тот же фрукт под двумя артикулами, например
«Хурма Королек дор (50)» и «Хурма королек (52)». Модель права, справочник 1С
содержит дубли.

### Тупики, которые не надо повторять

- **Сжатие DINOv2 в int8 ломает модель.** Совпадение векторов с исходными
  падает до 0,10 — это почти случайность. Поканальный вариант не помогает.
  Причина: у трансформеров после нормировки в активациях есть сильные выбросы.
  Вместо сжатия взята младшая модель того же семейства — она весит столько же,
  втрое быстрее и точность не теряет.
- **Zero-shot по текстовым описаниям** (CLIP «фотография бананов») даёт около
  50% на 28 классах по опубликованным замерам — как основной метод не годится.

## 3. Что сделано

### Компьютер (корень репозитория)

| Файл | Отвечает за |
|---|---|
| `build_index.py` | обход `photos/`, расчёт векторов, инкрементальная пересборка `index.npz` |
| `serve.py` | веб-страница: загрузить фото — увидеть похожее |
| `photos/` | эталоны: одна папка = один товар, имя папки = что покажет система |
| `index.npz` | база векторов, 1586 × 384 |

Зависимости в `requirements.txt`. Numpy закреплён ниже 2.0: на этой машине
Python собран под x86, для него PyTorch остановился на 2.2.2 и с numpy 2.x
не работает.

### Телефон (`android/`)

Полноценное приложение, всё считает на устройстве, интернет не нужен.

| Файл | Отвечает за |
|---|---|
| `Encoder.kt` (в `Recognizer.kt`) | ONNX-модель, кадр → вектор |
| `IndexStore.kt` | база: чтение, правка, экспорт и приём одним файлом |
| `MainActivity.kt` | камера, распознавание, добавление товара, дообучение кадром |
| `CatalogActivity.kt` | список товаров, обмен базой |
| `ProductActivity.kt` | снимки одного товара, удаление кадра, переименование |

Экраны:

```
Камера ── Распознать ──► пять вариантов
   │                        └─ тап ──► «Запомнить этот кадр?»
   ├── Новый товар ──► название + серия снимков
   └── Товары ──► список
                  ├─ тап ──────► снимки товара ──► тап ──► удалить кадр
                  │                             └──► переименовать
                  ├─ удержание ─► переименовать / удалить целиком
                  ├─ Поделиться базой ──► zip со всем содержимым
                  └─ Загрузить базу ────► принять zip
```

Подготовка файлов для телефона (`android/export/`):

```bash
.venv/bin/python android/export/export_onnx.py     # модель -> ONNX
.venv/bin/python android/export/export_thumbs.py   # миниатюры эталонов
.venv/bin/python android/export/export_index.py    # база -> assets
cd android && JAVA_HOME=$(brew --prefix openjdk@17) ./gradlew assembleDebug
```

APK около 119 МБ: 84 модель, 17 среда исполнения, 8 миниатюры, 2,3 база.

Обратный перенос: `android/export/import_from_phone.py база.zip` раскладывает
снимки с телефона по папкам `photos/`, дальше обычная пересборка.

### Инструменты сборки

JDK 17 через brew, Android SDK с платформой 34, Gradle 8.7 через wrapper.
Собирается только под `arm64-v8a` — иначе apk толстеет вдвое.

## 4. Что дальше

### Связь с весами и 1С — сделано

Найдена и реализована документация Масса-К «Протокол 100» (Мк.2.790.237РЭ):

```
кадр:  F8 55 CE | Len (int16 LE) | Command | данные | CRC-16-CCITT
CMD_GET_MASSA = 0x23, ответ CMD_ACK_MASSA = 0x24
тело ответа: масса int32, цена деления, флаги стабильности, нуля, тары
CRC считается начиная с байта Command, длиной Len
```

В документации сказано просто «CRC-16-CCITT», а это две разные начальные
константы. Приложение пробует обе и запоминает сработавшую.

Приложение умеет:
— спрашивать массу у настоящих весов (экран «Весы»)
— отдавать вес и штрихкод наружу по HTTP (экран «Для 1С»)
— притворяться весами Масса-К, чтобы штатный драйвер 1С брал вес без переделок

**Мост ESP32 и эмуляция сканера больше не нужны.** Вместо того чтобы толкать
данные в весы, приложение само стало устройством, у которого 1С забирает
и вес, и штрихкод.

Не проверено на живых весах — нужен доступ к сети магазина.

### Ближайшее и бесплатное

**Проверить связь с весами на месте.** Узнать IP и порт весов (они прописаны
в настройках 1С, раз весы уже с ней работают), вписать в приложении на экране
«Весы» и нажать «Получить вес».

**Снять кадры с натуры.** База сейчас собрана из картинок в интернете —
студийных, на белом фоне. Реальные снимки с площадки весов при магазинном
освещении дадут другую, честную точность. Первые же сто кадров с натуры
дадут больше, чем тысяча картинок из сети.

### Оборудование

Весы: **Масса-К серии ВПМ** с печатью этикеток. Есть Ethernet, RS-232 и USB
для периферии (в спецификации указан сканер штрихкодов). Принтер этикеток
уже внутри, покупать не надо. Штатный дисплей 192×64 — картинки не показать,
нужен свой экран.

Схема без вскрытия весов (важно: вскрытие лишает поверки, торговать нельзя):

```
   ВЕСЫ ВПМ (штатные, не трогаем)
        ├─ Ethernet ──── 1С выгружает товары (уже работает)
        └─ USB тип А ◄── наше устройство, притворяется сканером
                              ▲
                    телефон или Raspberry Pi
                    (камера + экран + распознавание)
```

Android не отдаёт приложениям режим USB-клавиатуры без рута, поэтому нужен
мост — **ESP32-S3** или Pi Pico W за тысячу рублей: принимает по сети «набери
12345» и печатает это как клавиатура.

### Важное про 1С

Драйвер для продажи **не нужен**. Поток данных: 1С выгружает товары в весы →
покупатель взвешивает → этикетка со штрихкодом → кассир сканирует на кассе →
там и регистрируется продажа. Взвешивание продажу не создаёт. Наше устройство
только помогает выбрать товар.

Подключение к 1С по OData уже сделано и проверено в соседнем проекте
`карточка_товара/retail_api.py` — оттуда берутся коды и цены.

## 5. Открытые вопросы

1. Принимают ли весы ввод от сканера — **проверить в первую очередь**
2. Реальная скорость на телефоне (ожидание 700–900 мс на Helio G85, не замерено)
3. Реальная точность на кадрах с натуры
4. Разделить визуально разные товары, слитые в один класс: капуста
   белокочанная / пекинская / цветная / красная различаются впятеро по цене
5. Дубли артикулов в 1С — модель их не различит и не должна; показывать оба
   варианта и давать выбрать
